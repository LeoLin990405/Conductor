# Super-agent article alignment

This is a mechanism-by-mechanism comparison with §§1–8 of the DeepSeek Harness Super-agent article. Source material is the internal document `SUPER-AGENT-ARTICLE-MAPPING` (not published) and the article itself: [the article page](https://haowenji.com/articles/x-2116829218935857152) and [the source post](https://x.com/DeepSeekHarness/status/2116857257245987236). Code references identify mechanisms present in this worktree. Owner labels identify feature scope; a separate branch name does not mean its work is integrated here. Nothing here claims production acceptance.

Status means: **Aligned** = the described mechanism exists; **Partial** = a related mechanism exists with a material scope or behavior gap; **Missing** = no equivalent mechanism or evidence exists. A lack of live acceptance is stated separately and does not by itself change a code mechanism's status.

## Source routing and trust behavior

GitHub and Feishu configs accept `routing_mode` values `respond-only-explicit`, `candidate` and `ignore`; missing legacy values default to `candidate`. `intake.py` drops ignored events and drops non-addressed events for `respond-only-explicit` before creating model work. `candidate` still passes through the global `accept_mode` and admission policy; it does not grant authority to act on inferred requests. This is a routing choice, not a trust label.

Source text remains stored as source data. Candidate prompt context marks source text as untrusted; Worker startup and delivered-input prompts do the same. `format_worker_input` JSON-quotes delivered text so fake marker strings remain content. Router instructions identify source text in candidate cards, Thread context and `autonomy_read` results as untrusted.

Security implementation references are `src/server/services/autonomy/github.py`, `src/server/services/autonomy/feishu.py`, `src/server/services/autonomy/security.py`, `src/server/services/autonomy/routing.py`, `src/server/services/autonomy/router.py`, `src/server/services/autonomy/worker.py` and `src/server/services/autonomy/inputs.py`. The optional Router model setting is `autonomy_router_model` in `src/config/settings.py`; it supports a separate configured model, but it does not train or specialize one.

## Channel model and reply norms

One channel model decides how a reply is written and whether it may leave the system at all: `src/server/services/autonomy/channels.py`. A Source resolves to exactly one channel — GitHub, Feishu, Slack, email, the local inbox, or the conservative "unconfigured" channel — and that channel carries its family (IM, asynchronous, local), its transport, its reply format, its limits, the sections it expects and its approval rules. `replies.py` resolves every reply through that model instead of branching on the Source kind, so a channel that has no transport no longer falls through to a GitHub comment.

The norms follow the article's two families. IM replies are capped at 100 words (one unit per CJK character), and a progress update is recorded but not delivered: an IM channel interrupts a person only for a decision, a question or a failure. Asynchronous channels are structured and information-dense: GitHub keeps its `### Summary` heading, and email renders a Subject line with named sections (`Summary`, `Background`, `Changes`, `Verification`) that a person reads before the mail is sent.

Approval is per channel, and it is durable. An email draft waits in the outbox as `pending_approval` until a person approves it through `POST /api/v1/autonomy/outbox/{id}/approve`; a draft they do not want is settled as `rejected`. The delivery effect only ever sends a `pending` row, so a held reply cannot leave the system by accident, and a reply a person has already read is delivered even though the channel asks for approval. A Source may set `require_approval` in its own config to tighten or loosen the channel default.
