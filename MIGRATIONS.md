# Migration order

Linear Alembic chain: `001` to `151`, one file per revision in `migrations/versions/`, no gaps and no branches. One head, and the head is **151** (`151_role_registry.py`, `down_revision = "150"`). A revision id is not reused.

## Rules

- One head. Two branches can each add the next number; after a merge both claim it. With two heads `alembic upgrade head` fails with "Multiple head revisions are present", and the start-up paths listed below stop before the server starts (`scripts/docker_entrypoint.sh` runs under `set -e`, the homelab compose command under `sh -ec`). `tests/unit/migrations/test_single_head.py` fails first.
- The revision id is the file's number as a string (`revision = "142"`), `down_revision` is the previous number, and every file's prefix matches its `revision`. `uv run alembic revision -m "<message>" --rev-id 143` writes `migrations/versions/143_<slug>.py` (the slug is the message lowercased, words joined by `_`) from `migrations/script.py.mako`: `Revises: 142` in the docstring, the typed header `revision: str = '143'` / `down_revision: Union[str, None] = '142'` (`_revision_graph` in `test_refactor_migrations.py` reads both the typed and the plain form), and `upgrade` / `downgrade` bodies that are only `pass`. Pass `--rev-id`, otherwise alembic picks its own id. Checked on a scratch copy of `migrations/`.
- The next revision is `152` with `down_revision = "151"`. Migrations are hand-written SQL in `op.execute()`: `migrations/env.py` sets `target_metadata = None` (no ORM models). `upgrade` starts with `SET LOCAL lock_timeout = '5s'`, as it does in every revision from 100 to 151; the template does not write that line, add it by hand.
- A revision id is never reused. Alembic keeps one script per id and only warns (`Revision N is present more than once`), so `_revision_graph` in `tests/unit/migrations/test_refactor_migrations.py` parses the files itself and fails when two files claim one id.
- When two lines want the same next id, the later line renumbers its unmerged file before it merges (the `chore(migrations): renumber ... to 123` through `... to 128` commits of 2026-11-03 did this). A revision already on the mainline keeps its id: a database that applied it has that id in `alembic_version`.
- Many tests walk the chain and pin the head: twenty files (seventeen under `tests/unit/migrations/` -- the ten per-revision files for 118, 119, 120, 122, 126, 128, 129, 130, 131 and 142, `test_refactor_migrations.py`, and the migration-144, migration-146, migration-147, migration-148, migration-149 and migration-151 tests -- plus `tests/unit/database/collab/test_collab_migration.py`, `tests/unit/scripts/test_refactor_status.py` and, outside the unit tree, `tests/integration/test_131_downgrade_atomic.py`, which asserts that `alembic_version` still reads `151` after a failed downgrade and needs PostgreSQL, so it is deselected by default). Adding a revision means updating those pins in the same change. `tests/unit/migrations/test_downgrades_one_transaction.py` and `tests/unit/migrations/test_141_dispatch_gates.py` name no revision above 142 and do not change when 144 is added.
- `cond doctor` compares the live public tables and columns with `src/conductor_cli/schema_snapshot.json` (a revision mismatch or a missing table or column is a FAIL line; an extra table or column is a WARN line; a database named `postgres` is skipped with a WARN). Adding a revision means regenerating it in the same change: `.venv/bin/python scripts/generate_schema_snapshot.py --maintenance "<libpq conninfo of a non-postgres database, e.g. template1>"` creates a scratch database `TEMPLATE template0`, migrates it to head, writes the snapshot and drops it. `tests/unit/conductor_cli/test_schema_drift.py` fails while the snapshot revision is not the head. Every connection the check and the script make refuses a database that libpq would resolve to `postgres` (`src/conductor_cli/db_guard.py`).
- `tests/unit/migrations/test_131_ticket_lines.py` reads this file and requires the three allocation strings `sa-a2a=128`, `beyond-endpoint=129-130` and `ob-tickets=131-132`. Keep them.

## Check and apply

```bash
uv run alembic heads      # 150 (head); reads the files only, needs no database
uv run alembic history    # newest first, e.g. "149 -> 150 (head), Migration 150: ..." (first docstring line)
uv run alembic current    # needs the database; prints the revision stored in alembic_version
uv run pytest tests/unit/migrations/ -q
make migrate              # uv run alembic upgrade head
uv run python -m scripts.refactor_status    # flag table, then "schema head (repo): **151** (database not read)"
uv run python -m scripts.refactor_status --database
                                            # also reads the database: "schema: database **151** · repo head **151** · migrated"
                                            # (the state is migrated / behind / ahead / unknown)
```

`migrations/env.py` builds the database URL from `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD` and `DB_SSLMODE` (defaults: `localhost`, `5432`, `postgres`, `postgres`, `prefer` for host, port, name, user and sslmode), loading `.env` from the project root. A `sqlalchemy.url` set before `env.py` runs wins (the integration fixture in `tests/integration/conftest.py` does that). The application's pool reads the same variables (`src/server/database/pool.py`). A fresh database needs the `pgcrypto` and `pg_trgm` extensions (`CREATE EXTENSION IF NOT EXISTS` in 001 and 092).

Where `alembic upgrade head` runs:

- `make setup-db` (`scripts/start_db.sh`).
- The `backend` service of `docker-compose.yml`, and the optional `ssh-gateway` service, which waits for the backend to be healthy. Both are built from `deploy/Dockerfile.dev`, whose `ENTRYPOINT` is `scripts/docker_entrypoint.sh` (wait for `pg_isready`, migrate, then `exec` the command).
- the maintainer's homelab deployment (not published), in the backend command before uvicorn starts. That service builds `deploy/Dockerfile.backend`, which migrates nothing by itself: its `CMD` is `server.py`, and the only `alembic` use under `src/` is the `conductor deploy` command. Not verified: whether a deployment outside this repository adds the step.
- `conductor deploy` (`src/conductor_cli/operations.py`): it takes a custom-format `pg_dump` backup and checks it with `pg_restore --list`, fast-forward pulls the checkout, runs `.venv/bin/alembic upgrade head`, restarts the backend and waits for `/health`; `--dry-run` prints the plan.

`conductor rollback --commit <sha> --backup <dump>` asks you to type `ROLLBACK`, stops the backend, runs `git reset --hard`, restores the dump with `pg_restore --clean --if-exists --no-owner --exit-on-error --single-transaction` and restarts the backend. It does not run `alembic downgrade`, so the Downgrade column below applies to a hand-run `alembic downgrade` only.

Downgrades, checked on a scratch PostgreSQL 16.15 database (empty tables, apart from the rows each check inserted): `alembic downgrade 123` ran 17 steps (undoing 140 down to 124) and `alembic upgrade head` ran them back to 140. alembic runs one command in one transaction (the block below says for which range), so a guard that refuses inside that range changes nothing; the guards are at 137, 138 and 139, inside it: with a `merge_started` row present, `alembic downgrade 138` raised at 139 and `alembic current` still printed 140, with the 140 tables still there; with an active `memory_tool_denials` row, `alembic downgrade 137` raised at 138 and the database stayed at 138; with a `memory_consolidation` proposal present, `alembic downgrade 136` raised at 137 and the database stayed at 138, and once the proposal was deleted the same command completed and `thread_id` / `task_run_id` were `NOT NULL` again.

The first two lines of the block above are what `tests/unit/migrations/test_downgrades_one_transaction.py` and `tests/integration/test_131_downgrade_atomic.py` pin. The unit test does not parse SQL, which two earlier versions of the pin tried and which each missed a spelling (`COMMIT; BEGIN` in one string, a `--` comment ended by a carriage return, `standard_conforming_strings` off). It checks that alembic emits one `BEGIN` and one `COMMIT` when it renders the range (an `autocommit_block` makes it emit another pair). And it searches, as whole words with no regard for quotes or comments, the source of every downgrade in the range (with the module-level functions and constants it names) and the SQL it renders, for the words that end or begin a transaction, change how SQL text is read, change a setting past the revision or reach the connection: `commit`, `rollback`, `begin`, `end`, `autocommit_block`, `standard_conforming_strings`, `set_config`, `reset`, `discard`, any `SET` that is not `SET LOCAL`, `lock_timeout` unless it is exactly the one `SET LOCAL` statement the block names, and others. Whatever those words find has to lie inside an exact text the test lists (the plpgsql `DO` guards, a few `UPDATE .. SET` and `ALTER COLUMN .. SET NOT NULL` clauses, two comments), and each such text must occur exactly the listed number of times: a text that is altered, duplicated or gone fails it, and so does any other occurrence of those words, `END; BEGIN` in place of a guard included. It also fails on an import other than `from alembic import op`, a decorator, or a call at module level. Copies of 130 with each of the changes listed in the test (the spellings above, a block, `getattr`, a helper, a plain `SET`, a `RESET`, `DISCARD`) and copies of 139 with its guard changed in each way listed there were required to fail it. What it cannot see is a downgrade that behaves differently online than offline and avoids all those words, SQL that builds a keyword at run time, and session state that is not a setting (temporary tables, advisory locks, `LISTEN`); a downgrade that needs the database to render fails the render instead (039 and 072, below the range, do). 131 used to be the exception. ## 142

`142_memory_forget_unsupported.py` follows 141 and widens the CHECK on `memory_forget_provider_notices.status` with `unsupported`. The notice records what happened to one copy of a forgotten memory: `unavailable` says that a copy could not be erased *right now*, which is what an outage looks like, and it does not say that the provider has no such operation at all. The remote MemFW of contract v2 is exactly that case -- it offers `/search`, `/stage` and `/related`, and no forget endpoint -- so the forget result says `unsupported` and the notice keeps it. The rows that exist keep their status: the new value is one the old vocabulary did not have, not a replacement for one it had.

The status says *that* the provider cannot forget; it does not say *why*. The Planner's ruling on the notice is a reason of its own, and the revision adds `memfw_reason` to hold it beside the status it explains (`src/server/database/refactor/memory.py`, `record_forget_provider_notices`, which writes it in the same INSERT and updates it on conflict). It is nullable on purpose: a ruling outside the vocabulary is stored as NULL rather than costing the notice its row, and the write logs the stable code `reason_not_in_vocab` and never the ruling itself. The CHECK on the column is the *forget* vocabulary, spelled out verbatim and small on purpose -- `no_forget_endpoint` (the remote MemFW has no forget endpoint, which is what contract v2 is), `not_supported` (the remote says so itself) and `remote_rejected` (the remote refused) -- or NULL, so a database that has applied 142 refuses a ruling no forget ever makes, the same boundary `memory_forget_tombstones.reason` holds for a forget of our own. It is emphatically *not* the contract's `/related` reasons, `link` and `lexical` and the rest: those say why one memory sits next to another, which has nothing to do with a forget. The ruling reaches the row through the forget result's carrier and the notice the service hands over (`src/server/services/refactor/memory_forget.py`, `_notify_rows`), and comes back out of it through the owner-scoped read-back `forget_provider_notices`, which a first forget and a retry both call once their write is behind them, so the API answers with the stored `provider`, `status` and `memfw_reason` rather than with what the federation said on the way through.

The downgrade is a redeploy of the previous build, and the previous build cannot read `unsupported`, so the notices that carry it become `unavailable` -- the nearest status the old vocabulary has -- *before* the old CHECK is restored. The order is the point: restoring the CHECK first would fail on those rows. The column goes first of all, since dropping it drops the CHECK on it with it and leaves the rewrite unconstrained by the new vocabulary. The check constraint of migration 133 is not touched; 133 stays as it was written.

## 143

`143_drop_finance_tables.py` follows 142 and removes what the finance vertical left behind, now that nothing in `src/` reads or writes any of it: `chart_annotations` (014), `watchlist_items` and `watchlists` (001), `user_portfolios` (001), `market_insights` (001, widened by 005 and 007), `market_watch_targets` (077), `wakeups` (082), and the `investment_preference` column. The column is the one 001 created beside `risk_preference` and `agent_preference` on the preferences row -- `users` itself has no such column -- and the table it sits on stays, because the rest of `user_preferences` (the agent preference, the model selection, the BYOK flags) is still read and written. The `users` table is untouched, and so is `computer_data_tokens`, which W10c-2 drops once W10b-1 is done.

**The rows are destroyed and cannot be restored.** No other table holds a copy, nothing is archived first, and no backup is taken here; the downgrade rebuilds the schema empty. A rollback that needs the watchlists, the holdings, the insights, the targets or the wakeups restores a backup taken before this migration (`conductor rollback`, which does not run `alembic downgrade`), not an empty set of tables.

`upgrade` runs in one transaction, children before parents: `watchlist_items` references `watchlists`, so it goes first; `market_watch_targets` and `wakeups` reference `conversation_threads` and `chart_annotations` references `workspaces`, both of which stay, and nothing references a table this revision drops. Each `DROP TABLE` takes its indexes, its constraints and its `updated_at` trigger with it, and every statement is `IF EXISTS`, so a re-run is a no-op rather than a failure. The column is dropped with `DROP COLUMN IF EXISTS` on the table that keeps its other columns.

`downgrade` is **structural only**: it restores the shape 142 had and none of the data. It recreates each table with the columns, indexes and constraints its creating migration gave it -- 001 for the watchlist, holding and insight tables (`market_insights.user_id` as 007 left it, `VARCHAR(255)`), 014 for `chart_annotations`, 077 for `market_watch_targets`, 082 for `wakeups` -- in the reverse order, parents before children, plus 001's three `updated_at` triggers and 014's, and puts `investment_preference` back with the JSONB default 001 gave it. Every statement is `IF NOT EXISTS` and each trigger is dropped before it is created, so a re-run, or one against a database where a later revision already restored a table, leaves what is there alone instead of failing. The guarantee is that the schema is back, not that the history is. The one thing that cannot come back exactly is the column's place: `ADD COLUMN` appends, so `investment_preference` returns at the end of `user_preferences` rather than the position 001 gave it, with its type, its default and its nullability intact and no reader naming it by position. The foreign keys it creates hold `SHARE ROW EXCLUSIVE` on `users`, `watchlists` and `conversation_threads` until the command's transaction commits (077 and 082 describe the same discipline), so run it with the backend stopped, as the recovery notes above say.

"its creating migration gave it" is not the whole story, which is the one way this goes wrong: 096 removed trading and dropped `idx_wakeups_armed_order` beside `order_attempts`, so replaying 082 alone puts an index back that 142 never had. The downgrade therefore does not create that one index, and `tests/integration/test_143_drop_finance_tables.py` checks the result rather than the list: it builds one database at 142 from a fresh chain, runs another to 143 and back, and compares every column, constraint, index, relation, function and trigger of the two `public` catalogs, tolerating only the column's ordinal position. It needs PostgreSQL, so it is deselected by default like the other integration migration tests.

`148_memory_class_about.py` follows 147 and gives the memory projection the two columns of the shared-memory ontology (the internal planning note `memory-ontology` (not published), O7): `class` -- what kind of claim a memory is (`Preference`, `Constraint`, `Lesson`, ...) -- and `about` -- the concept id of the thing the memory is about (`project:conductor`, `person:leo`). Both are nullable `TEXT`, and both stay NULL for a memory written before the ontology existed: the projection never invents a class or a concept for a row that does not name one, and the browse-by-concept page shows an unclassified row as such rather than guessing.

The index `ix_memory_entries_class_about` covers the pair, because the page reads it two ways at once: a class filter (every `Preference`) and an about filter (every memory about one concept). A single-column index on `class` alone would not answer the second question, and the pair index answers the first as a prefix scan.

The `about` column holds one concept, because a column holds one value. A memory may name several, and the full list stays in the row's `metadata`, which is where the browse page and the Ticket audit read it: a memory about two things belongs to both concept groups, and an audit of it names both. The pair index still answers the common case, where the concept asked for is the one the column holds.

The downgrade drops the index and then both columns, in that order, because dropping a column takes its indexes with it; the statements are `IF EXISTS`, so a re-run is a no-op. Nothing else changes: the rows, their status, their metadata and their forget tombstones stay as they are, and the two columns held no data the rest of the schema depended on.

## 149

`149_dispatch_workspaces.py` follows 148 and adds the dispatch workspace registry: one row per git checkout an auto-dispatch run may use. `path` is the repo root, `git_remote` the remote a `git fetch` updates, `sandbox_policy` the sandbox setting its workers inherit, and `default_worker` the worker provider a dispatch starts with when it names none. The launch script consumes the policy before starting a Worker: `workspace-write` (or the empty default) runs the write worker, `read-only` is refused because a WORK line must write and commit the checkout, and an unknown value is refused rather than silently widening the sandbox. `name` is unique per user, so the CLI can address a row by name as well as by id.

The drive, its planner, its gates and every recovery read the snapshot, so editing or deleting the registry row cannot move work that is already running. The columns are text with an empty default and no foreign key, for the same reason the registry has none: history must outlive the row it names.

The downgrade drops the four dispatch columns, then the two lookup indexes, the unique index and the table; the statements are `IF EXISTS`, so a re-run is a no-op. The checkout on disk is never touched by this revision.
